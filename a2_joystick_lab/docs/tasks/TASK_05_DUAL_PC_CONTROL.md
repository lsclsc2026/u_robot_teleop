# Task 05：双机中继真机控制与速度挡位

## ① 实验背景

最终目标是由未配对遥控器控制 PC1，PC1 经 WiFi 把指令发给 PC2，PC2 再经网线转发到 Unitree 下位机并控制 A2。本 Task 在 Task 04 的 dry-run 基础上开启真实 `SportClient`，并进一步验证原生低速/高速挡位。

## ② 实验流程

```text
遥控器 → BLE → PC1
→ WiFi UDP → PC2 中继
→ 有线 UDP → Unitree
→ 原生按钮映射 + SportClient
→ A2 真机运动
```

速度逻辑保持官方两档：`UP` 只切高速、`DOWN` 只切低速；重复按 `UP` 不进入跑步，只有 `L2+Start` 才切换跑步模式。最新实验同时记录 `gait`、`speed_level` 和实际发送速度。

## ③ 实验结果

全链路真机实验：

- PC1 收到 12133 个 ACK，实际调用移动 API 5658 次、动作接口 10 次。
- BLE→首次发送 p50 `0.176 ms`；端到端 RTT p50 `38.046 ms`。
- PC2 中继处理 p50 `67.5 μs`，PC2→Unitree ACK p50 `1.373 ms`。
- 实际体感中，控制延迟可接受，运动基本与操作同步。

速度挡位实验：

- 10493 个 ACK 连续，无内部缺失或重复。
- `walk/low` 7364 帧，`walk/high` 3129 帧，没有出现 `run`。
- 低速最大实测：`vx=0.724、vy=0.481、yaw=1.868`。
- 高速最大实测：`vx=1.345、yaw=2.205`。
- `UP/DOWN` 动作返回 0，低速和高速体感差异得到确认。

## ④ 分析

本 Task 已完成功能闭环：遥控器输入经过 PC1、PC2 和 Unitree 后可以真实控制 A2，且 `UP/DOWN` 只切换行走速度，没有误进入跑步。PC2 中继和有线段仍然很快。

需要注意，较长实验中出现两个大段 ACK 缺口，并伴随 `SportClient` 的 `3104` 超时；这说明同步动作调用仍可能阻塞或影响 ACK 返回。虽然真机体感可接受，但在提高速度和长期运行前，应改为“UDP 接收线程 + 最新指令执行线程”，避免积压旧运动帧。视频延迟属于独立的图传链路问题，不应与控制 RTT 混合统计。
